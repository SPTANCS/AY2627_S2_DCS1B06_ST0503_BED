03
GET
/snacks/:id
Find One Snack by ID
Look up a specific item — and handle when it doesn't exist

A customer walks up and asks: "Do you have item number 7?" This introduces a new concept: route parameters. The :id in the URL is a placeholder — Express captures whatever the user puts there and hands it to you in req.params.

  • /snacks/3 → return the matching snack object
  • /snacks/99 → ID doesn't exist, return { "error": "Item not found" }
Expected behaviour
GET /snacks/3 → { "id": 3, "name": "Candy Bar", "price": 1.25, "quantity": 80 }
GET /snacks/99 → { "error": "Item not found" }
Express syntax — given to you
const id = req.params.id;  // always a string, e.g. "3"

// Find an item in an array by a condition:
const item = someArray.find(x => x.id === Number(id));
// → returns the matching object, or undefined if nothing matches
🧠 Think before you code

The ID from the URL is always a string like "3", but the IDs in the array are numbers like 3. Why does that matter when comparing with ===?

What does .find() return when nothing matches? How will you use that to decide what to send back?

Steps

  1. Read req.params.id and convert it to a number with Number().
  2. Use .find() to search the snacks array for a matching id.
  3. If found → respond with the item using res.json().
  4. If not found → respond with { "error": "Item not found" }.
  5. Test both a valid and an invalid ID in Swagger UI, then run npm test.

05
GET
/
The Store's Front Door
Follow along — return everything, or filter by ?category

The root route is the store entrance. By default it shows both shelves. But customers can pass a ?category= query parameter to browse just one section. This introduces query parameters — optional key-value pairs appended to the URL after a ?.

  • No params → return { snacks: [...], electronics: [...] }
  • ?category=snacks → return only the snacks array
  • ?category=electronics → return only the electronics array
  • ?category=drinks or any other value → return an error message
Expected behaviour
GET / → { snacks: [...], electronics: [...] }
GET /?category=snacks → [ all 10 snacks ]
GET /?category=drinks → { "error": "..." }
Express syntax — given to you
const category = req.query.category;
// → "snacks", "electronics", or undefined if not provided
🧠 Think before you code

There are three distinct outcomes. Map them out before touching the keyboard:

  • No category param at all → what do you return?
  • category is "snacks" or "electronics" → what do you return?
  • category is something else → what do you return?

What's the cleanest order to check these three cases? Does it matter which you handle first?

Steps

  1. Read req.query.category — it will be a string or undefined.
  2. If no category was provided, respond with { snacks, electronics }.
  3. If it's "snacks" or "electronics", respond with just that array.
  4. Otherwise, respond with an error message: { "error": "Invalid category" }.
  5. Test all four cases in Swagger UI, then run npm test.

Filter by Price
On your own — extend GET / with ?maxPrice

Still in the same GET / handler from Q5. Now extend it — customers want to filter results by price. Add a ?maxPrice query param that works alongside ?category. This one requires more careful thinking — query params always arrive as strings, so you need to validate before you can use them.

  • No maxPrice → existing behaviour from Q5 unchanged
  • ?maxPrice=5 → filter whichever items are being returned to price <= 5
  • ?maxPrice=abc → not a number, return an error message
  • ?maxPrice=-10 → negative number, return an error message
  • ?category=snacks&maxPrice=3 → both params work together
Expected behaviour
GET /?maxPrice=3 → { snacks: [ Candy Bar, Popcorn, Chips ], electronics: [] }
GET /?category=snacks&maxPrice=3 → [ Candy Bar $1.25, Popcorn $1.99, Chips $2.99 ]
GET /?maxPrice=abc → { "error": "..." }
JS helpers — given to you
const raw = req.query.maxPrice;      // string or undefined
const price = parseFloat(raw);       // converts "3.5" → 3.5, "abc" → NaN
isNaN(price);                         // true if conversion failed

items.filter(item => item.price <= price); // keep only affordable items
🧠 Think before you code

Before filtering, you need to validate. What are all the ways maxPrice could be bad input?

  • What if the user doesn't send it at all?
  • What if they send a word like "cheap"?
  • What if they send a negative number?
  • What if they send 0? Should that be allowed or rejected?

Sketch the decision tree on paper first. Then translate it into if statements.

Steps

  1. Still inside app.get('/', ...) — don't create a new route.
  2. Read req.query.maxPrice. If it's undefined, skip all filtering.
  3. Convert it to a number with parseFloat(). If it's NaN or negative, return an error message.
  4. Apply the filter to whichever item(s) you're about to return — after the category logic from Q5.
  5. Test in Swagger: try /?maxPrice=5, /?category=snacks&maxPrice=3, and /?maxPrice=abc.
  6. Run npm test.

Sort by Price
On your own — add ?sort so all three params work together

Still the same GET / handler. Add one more layer — a ?sort param so customers can order results by price. By the end of this question, all three params — ?category, ?maxPrice, and ?sort — should work individually and in any combination together.

  • No sort param → existing behaviour from Q6 unchanged
  • ?sort=asc → sort results by price, cheapest first
  • ?sort=desc → sort results by price, most expensive first
  • Any other value (e.g. ?sort=random) → return an error message
  • ?category=snacks&maxPrice=5&sort=asc → all three params work together
Expected behaviour
GET /?category=snacks&sort=asc → [ Candy Bar $1.25, Popcorn $1.99, Chips $2.99, ... ]
GET /?category=snacks&maxPrice=4&sort=desc → [ Granola Bar $2.50, Chips $2.99, Popcorn $1.99, ... ]
GET /?sort=random → { "error": "..." }
JS sort syntax — given to you
// Ascending (cheapest first):
items.sort((a, b) => a.price - b.price);

// Descending (most expensive first):
items.sort((a, b) => b.price - a.price);

// ⚠️ .sort() modifies the array in place — sort a copy to be safe:
let result = [...items];  // spread creates a shallow copy
result.sort((a, b) => a.price - b.price);
🧠 Think before you code

You now have three params that can all appear at once: ?category, ?maxPrice, and ?sort. What order should you apply them?

Try it on paper: take the full snacks + electronics data, apply category first, then maxPrice, then sort. Does it matter if you swap the order? Could sorting before filtering ever give a wrong result?

Also: .sort() modifies the array in place. If you sort the original snacks array, what happens the next time someone hits GET /? How do you prevent that?

Steps

  1. Still inside app.get('/', ...) — don't create a new route.
  2. Read req.query.sort. If it was provided but isn't "asc" or "desc", return an error message.
  3. Make sure you're working on a copy of the data, not the original array — so the sort doesn't persist between requests.
  4. Apply category filtering first, then maxPrice filtering, then sorting.
  5. Test all combinations in Swagger: /?sort=desc, /?category=snacks&sort=asc, /?category=electronics&maxPrice=20&sort=asc, /?sort=random.
  6. Run npm test — all tests should be green. 🎉
