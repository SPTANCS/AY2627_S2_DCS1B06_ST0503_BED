The Big Picture: Layer by Layer
How an Express.js server handles a request end-to-end

Modern backend applications are built in layers. Each layer has a single, clear responsibility. When a client (browser, mobile app, Postman) sends a request, it travels through all these layers before a response is returned.

  [ Client / Browser ]
         |
         |  HTTP Request (e.g. GET /todos)
         v
  +------------------+
  |    Route Layer   |  Receives the URL, decides who handles it
  +------------------+
         |
         v
  +------------------+
  | Controller Layer |  Reads request data, runs the queries, sends the response
  +------------------+
         |
         v
  +------------------+
  |   Drizzle ORM    |  Builds and executes type-safe SQL queries
  +------------------+
         |
         v
  +------------------+
  | SQLite / libsql  |  The actual database file on disk
  +------------------+
         |
         |  Data travels back up through each layer
         v
  [ Client receives JSON response ]

Full request/response flow in an Express + Drizzle application

Each layer has one job:

Route — Matches the URL and HTTP method, delegates to a controller.
Controller — Extracts params/body from the request, runs the Drizzle queries, sends the response with the correct status code.
Drizzle ORM — Translates JavaScript method calls into SQL statements.
Database — Executes the SQL and returns rows.

Q1. A controller receives req.params.id = 5 and needs to fetch a to-do from the database. Whose job is it to write the SQL query?
The controller writes SQL directly
The Route parses the SQL from the URL
Drizzle ORM generates the SQL from JavaScript method calls
The database generates its own queries
Correct!
Correct! Drizzle ORM is the layer that converts JavaScript calls like .select().from(todos).where(eq(todos.id, 5)) into the actual SQL that the database runs.
Not quite.
Not quite. Drizzle ORM sits between your application code and the database, translating JavaScript method calls into raw SQL statements automatically.

Defining Tables: The Drizzle Schema
Primary keys, foreign keys, and how relationships are expressed in code

In Drizzle, you define your tables in a schema file using JavaScript. This schema describes the structure of your database: the tables, their columns, and the relationships between them.

Do not create any files yet. Read this section to understand what each line does. You will be told exactly when to create src/db/schema.js and type this in — that is in Section 3.

javascript
// src/db/schema.js
import { sqliteTable, integer, text } from 'drizzle-orm/sqlite-core';

export const users = sqliteTable('users', {
  id:        integer('id').primaryKey({ autoIncrement: true }),
  username:  text('username').notNull().unique(),
  email:     text('email').notNull().unique(),
  createdAt: integer('created_at', { mode: 'timestamp' }).notNull(),
});

// One-to-many: one user can have many todos
export const todos = sqliteTable('todos', {
  id:        integer('id').primaryKey({ autoIncrement: true }),
  userId:    integer('user_id').notNull().references(() => users.id),
  title:     text('title').notNull(),
  completed: integer('completed', { mode: 'boolean' }).notNull().default(false),
  dueDate:   integer('due_date', { mode: 'timestamp' }),
});

// One-to-one: one user has exactly one profile
export const userProfiles = sqliteTable('user_profiles', {
  id:        integer('id').primaryKey({ autoIncrement: true }),
  userId:    integer('user_id').notNull().unique().references(() => users.id),
  bio:       text('bio'),
  avatarUrl: text('avatar_url'),
});

Primary Keys

Every table should have a primary key — a column that uniquely identifies each row. No two rows can share the same primary key value, and it can never be NULL. In Drizzle you declare it with .primaryKey().

The autoIncrement: true option tells the database to automatically assign the next available integer when a new row is inserted. This means you never supply an id manually — the database handles it.

Drizzle: integer('id').primaryKey({ autoIncrement: true })
SQL: id INTEGER PRIMARY KEY AUTOINCREMENT

 You insert two rows without specifying id:

  db.insert(todos).values({ userId: 1, title: 'Buy groceries', completed: false });
  db.insert(todos).values({ userId: 1, title: 'Finish report',  completed: false });

  The database assigns ids automatically:
  +----+---------+---------------+-----------+
  | id | user_id | title         | completed |
  +----+---------+---------------+-----------+
  |  1 |    1    | Buy groceries |     0     |  <-- id = 1 (first row ever inserted)
  |  2 |    1    | Finish report |     0     |  <-- id = 2 (next available)
  +----+---------+---------------+-----------+

autoIncrement: you never supply the id — the database assigns the next integer automatically

Foreign Keys and Relationships

A foreign key is a column whose value must match a primary key in another table. It is how you link rows across tables and encode relationships. In Drizzle you declare one with .references(() => targetTable.column).

The arrow function syntax (() =>) is required so Drizzle can resolve the reference even if the target table is defined later in the same file — this avoids circular reference errors in JavaScript.

One-to-Many One-to-One
One user can have many to-dos. One user has exactly one profile.
The foreign key has no unique constraint — the same user_id can appear in many rows. The foreign key has .unique() — no two rows can share the same user_id.
userId: integer('user_id')
  .notNull()
  .references(() => users.id)		 userId: integer('user_id')
  .notNull()
  .unique()
  .references(() => users.id)
SQL: user_id INTEGER NOT NULL REFERENCES users(id) SQL: user_id INTEGER NOT NULL UNIQUE REFERENCES users(id) 
 ONE-TO-MANY  (users -> todos)

  users                     todos
  +----+----------+         +----+---------+---------------+
  | id | username |         | id | user_id | title         |
  +----+----------+         +----+---------+---------------+
  |  1 | alice    |<---+--- |  1 |    1    | Buy groceries |
  |  2 | bob      |    +--- |  2 |    1    | Finish report |
  +----+----------+    +--- |  3 |    1    | Call dentist  |
                            |  4 |    2    | Read a book   |
                            +----+---------+---------------+
  The same user_id can repeat many times -- no UNIQUE constraint.


 ONE-TO-ONE  (users -> user_profiles)

  users                     user_profiles
  +----+----------+         +----+---------+------------------+
  | id | username |         | id | user_id | bio              |
  +----+----------+         +----+---------+------------------+
  |  1 | alice    |<------- |  1 |    1    | Loves coding     |
  |  2 | bob      |<------- |  2 |    2    | Enjoys hiking    |
  +----+----------+         +----+---------+------------------+
  user_id has UNIQUE -- each value can only appear once.

The only difference in Drizzle between 1-to-many and 1-to-1 is .unique() on the foreign key

💡

The foreign key always lives on the table that represents the "many" side (or the dependent side in a 1-to-1). A to-do belongs to a user, so user_id is on the todos table — not on users.

You never write the SQL below, and you should not type it anywhere. This is the SQL that drizzle-kit push generates from your schema and runs against the database for you. It is shown here only so you can see exactly what each Drizzle option produces:

javascript
-- Generated SQL
CREATE TABLE users (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  username   TEXT NOT NULL UNIQUE,
  email      TEXT NOT NULL UNIQUE,
  created_at INTEGER NOT NULL
);

-- One-to-many: no UNIQUE on user_id
CREATE TABLE todos (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id    INTEGER NOT NULL REFERENCES users(id),
  title      TEXT NOT NULL,
  completed  INTEGER NOT NULL DEFAULT 0,
  due_date   INTEGER
);

-- One-to-one: UNIQUE on user_id prevents duplicates
CREATE TABLE user_profiles (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id    INTEGER NOT NULL UNIQUE REFERENCES users(id),
  bio        TEXT,
  avatar_url TEXT
);
Q1. You are modelling a school system where each student has exactly one student card. Which Drizzle snippet correctly represents the student card's foreign key?
studentId: integer('student_id').notNull().references(() => students.id)
studentId: integer('student_id').notNull().unique().references(() => students.id)
studentId: integer('student_id').primaryKey().references(() => students.id)
studentId: text('student_id').notNull().references(() => students.id)
Correct!
Correct! Because it is a 1-to-1 relationship, the foreign key needs .unique() to ensure no two student cards can belong to the same student.
Not quite.
Not quite. A 1-to-1 relationship requires .unique() on the foreign key column. Without it, multiple student cards could reference the same student — making it a 1-to-many relationship instead.
Q1. You insert a new to-do without providing an id value. What happens?
Drizzle throws an error because id is required
The row is inserted with id = 0 by default
The database automatically assigns the next available integer as the id
The id column is left as NULL
Correct!
Correct! autoIncrement: true means the database tracks the last used id and assigns the next integer automatically every time a row is inserted.
Not quite.
Because id is declared with autoIncrement: true, the database assigns it automatically. You never need to (or should) supply it yourself when inserting a new row.

04
Drizzle ↔ SQL: Side by Side
Every Drizzle method call translates to a specific SQL statement

Drizzle is not magic — it is a query builder. Every method you chain eventually produces a SQL string that gets sent to the database.

Nothing in this section is to be typed into a file. Read it once to see the pattern, then treat it as a lookup table you come back to while writing your controllers in Section 5 and Section 6.

SELECT — Fetch all rows

Drizzle (JavaScript) Generated SQL
db.select().from(todos) SELECT * FROM todos

SELECT — Specific columns only

Drizzle (JavaScript) Generated SQL
db.select({
  id: todos.id,
  title: todos.title
}).from(todos)		 SELECT id, title
FROM todos

SELECT — With a WHERE filter

Drizzle (JavaScript) Generated SQL
db.select().from(todos)
.where(eq(todos.userId, 1))		 SELECT * FROM todos
WHERE user_id = 1

INSERT — Add a new row

Drizzle (JavaScript) Generated SQL
db.insert(todos).values({
  userId: 1,
  title: 'Buy groceries',
  completed: false
}).returning()		 INSERT INTO todos
(user_id, title, completed)
VALUES (1, 'Buy groceries', 0)
RETURNING *

UPDATE — Modify existing rows

Drizzle (JavaScript) Generated SQL
db.update(todos)
.set({ completed: true })
.where(eq(todos.id, 1))
.returning()		 UPDATE todos
SET completed = 1
WHERE id = 1
RETURNING *

DELETE — Remove rows

Drizzle (JavaScript) Generated SQL
db.delete(todos)
.where(eq(todos.id, 1))		 DELETE FROM todos
WHERE id = 1

JOIN — Combine data from two tables

Drizzle (JavaScript) Generated SQL
db.select({
  owner: users.username,
  task: todos.title
})
.from(todos)
.innerJoin(users,
  eq(todos.userId, users.id))		 SELECT users.username,
       todos.title
FROM todos
INNER JOIN users
  ON todos.user_id = users.id
⚠️

Always include a .where() clause on UPDATE and DELETE statements. Without one, Drizzle will update or delete every row in the table — there is no confirmation prompt.

Common filter operators — import these from drizzle-orm:

SQL: WHERE id = 1
Drizzle: .where(eq(todos.id, 1))
SQL: WHERE completed != 1
Drizzle: .where(ne(todos.completed, true))
SQL: WHERE id > 5
Drizzle: .where(gt(todos.id, 5))

SQL: WHERE due_date <= 1700000000
Drizzle: .where(lte(todos.dueDate, timestamp))
SQL: WHERE user_id = 1 AND completed = 0
Drizzle: .where(and(eq(todos.userId, 1), eq(todos.completed, false)))
SQL: WHERE title = 'Shopping' OR title = 'Laundry'
Drizzle: .where(or(eq(todos.title, 'Shopping'), eq(todos.title, 'Laundry')))
SQL: WHERE title LIKE 'Buy%' (starts with 'Buy')
Drizzle: .where(like(todos.title, 'Buy%'))

% matches any sequence of characters. _ matches exactly one character.
SQL: WHERE due_date IS NULL
Drizzle: .where(isNull(todos.dueDate))
Q1. You want to fetch all incomplete to-dos that belong to user 2. Which Drizzle call is correct?
db.select().from(todos).where(eq(todos.userId, 2), eq(todos.completed, false))
db.select().from(todos).where(and(eq(todos.userId, 2), eq(todos.completed, false)))
db.select().from(todos).filter(userId == 2 && completed == false)
db.select().from(todos).where(eq(todos.userId, 2)).where(eq(todos.completed, false))
Correct!
Correct! Use and() to combine multiple conditions inside a single .where() call. It maps to SQL's WHERE user_id = 2 AND completed = 0.
Not quite.
Not quite. To combine multiple conditions, wrap them in and(...): .where(and(eq(todos.userId, 2), eq(todos.completed, false))). Chaining two .where() calls or passing multiple arguments directly won't work as expected.

Stage 1 — The Route
The router receives the HTTP request and hands it to the correct controller function. It does nothing else: no database access, no logic, no validation.

Do this now: create src/routes/todoRoutes.js and type in the code below.

javascript
// src/routes/todoRoutes.js
import express from 'express';
import { getTodosByUser } from '../controllers/todoController.js';

const router = express.Router();

// GET /users/:userId/todos
router.get('/users/:userId/todos', getTodosByUser);

export default router;

The route's only job is to map GET /users/:userId/todos to the getTodosByUser function. It does not touch the database or contain any logic.

Your editor will show an error on the import line until you create the controller in the next stage. That is expected — carry on.

Stage 2 — The Controller
The controller extracts data from the request, validates it, runs the Drizzle query, and sends the HTTP response with an explicit status code.

Do this now: create src/controllers/todoController.js and type in the code below. You will add more handlers to this same file in Section 6, so leave it open.

javascript
// src/controllers/todoController.js
import { db } from '../db/connection.js';
import { todos } from '../db/schema.js';
import { eq } from 'drizzle-orm';

export async function getTodosByUser(req, res) {
  const userId = parseInt(req.params.userId);

  if (isNaN(userId)) {
    return res.status(400).json({ error: 'Invalid user ID' });
  }

  const result = await db
    .select()
    .from(todos)
    .where(eq(todos.userId, userId));

  return res.status(200).json(result);
}

The controller does three things in order:
1. Validates the input (parseInt + NaN check).
2. Queries the database via Drizzle.
3. Responds with an explicit status code and JSON.

💡

Always write res.status(...).json(...) rather than a bare res.json(...). Express defaults to 200 when you omit the status, which means a success and an error can look identical in your code. Stating the status explicitly makes the intent of every response obvious to whoever reads the controller next — including your marker.

return res.status(200).json(result);
The request succeeded and the body contains the requested or updated data.
return res.status(201).json(newTodo);
A new row was created. Send back the created row (this is where .returning() earns its keep).
return res.status(400).json({ error: 'Invalid user ID' });
Failed validation: a non-numeric id, a missing required field, a malformed body.
return res.status(404).json({ error: 'To-do not found' });
The id was valid, but no matching row came back from the query.
return res.status(500).json({ error: 'Internal server error' });
Used inside a catch block when the database or your own code throws.
💡

Always validate and sanitize req.params and req.body before passing values to a query. URL parameters arrive as strings, and a user could send anything — including NaN, negative numbers, or malicious input.
