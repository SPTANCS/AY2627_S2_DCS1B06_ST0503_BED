02
function and Arrow Functions
We write functions so we do not repeat ourselves. Folder 01.

Let's start with a problem rather than with syntax.

Here is a price list with 9% tax added to each item. Open 01-functions and run node index.js in your terminal.

01-functions/index.js
javascript
console.log(3 * 1.09);   // tax on a $3 item
console.log(7 * 1.09);   // tax on a $7 item
console.log(12 * 1.09);  // tax on a $12 item

The rule for adding tax is written out three times.

If the rate changes, you have to find and fix three lines, and if you miss one you get a bug that looks like a rounding error.

A function lets you write the rule once and use it by name.

01-functions/index.js
javascript
function withTax(price) {
  return price * 1.09;
}

console.log(withTax(3));
console.log(withTax(7));
console.log(withTax(12));

That is the whole reason functions exist. One place to write a rule, one place to change it, and a name that says what it does.

There is a second way to write the same function, and it is the one you have been typing in your routes all week.

Run node index.js in your terminal again and compare the two lines of output.

01-functions/index.js
javascript
function withTaxA(price) {
  return price * 1.09;
}

const withTaxB = (price) => {
  return price * 1.09;
};

console.log(withTaxA(10));
console.log(withTaxB(10));

The output is identical.

These are not two different features. They are two ways of spelling the same thing, and either one can be translated into the other.

The arrow version is the one to slow down on. A function sitting on the right hand side of an = shows that a function is a value.

It can be stored in a variable, put in an array, or handed to something else.

💡

Both forms need return. A function body inside braces gives back nothing unless you say so.

💡

Tutorials online often use a shorter arrow form that drops the braces and the return. We use the braces form in this module because it matches the (req, res) => { ... } in your routes. If you meet the short form elsewhere, it does the same job.

Step 3 of 10
03
Functions as Arguments
A function is a value you can hand to something else. Folder 01. This answers question 2.

If a function is a value, it can be an argument.

Run node index.js in your terminal. Then answer one thing before reading on: who called the arrow function? You never wrote a line that calls it.

01-functions/index.js
javascript
const twice = (task) => {
  task();
  task();
};

twice(() => {
  console.log("hello");
});

twice takes a function as its argument and calls it two times. You wrote the arrow function, but twice decided when to run it and how often.

Nothing magic is happening here. task is an ordinary parameter that happens to hold a function, and task() is how you call it.

JavaScript itself works the same way. setTimeout takes a function and a number of milliseconds, and calls your function after that time has passed.

01-functions/index.js
javascript
setTimeout(() => {
  console.log("one second later");
}, 1000);

Your route is the same shape a third time.

app.get("/users", handler) hands your function over. You never call it. The server calls it, once per request, and passes in req and res when it does.

YOU WRITE THE FUNCTION                SOMETHING ELSE CALLS IT
----------------------                -----------------------

  (req, res) => {                       a request arrives
    res.json(users);                            |
  }                                             v
                                        handler(req, res)
         |                                      |
         | handed over as                       v
         | an argument                    your code runs
         v                                      |
  app.get("/users", handler)                    v
                                        ...and again, next request

You supply the function. The caller decides when and how often to run it.

Most of what you write in server code is not code that runs now. It is code you hand to something else to run later.

⚠️

Watch the parentheses when you pass a function by name. app.get("/users", listUsers) hands the function over. app.get("/users", listUsers()) calls it immediately and hands over whatever it returned, which is almost never what you want.

Check: Functions
Q1. Which of these returns undefined when you call it?
function f(n) { return n * 2; }
const f = (n) => { n * 2; };
const f = (n) => { return n * 2; };
Correct!
Correct. It calculates n * 2 and throws the answer away, because there is no return. Nothing crashes. It quietly gives back undefined.
Not quite.
Look for the one with no return inside the braces. A function body gives back nothing unless you write return, whichever way the function was spelled.
Q2. In app.get("/users", (req, res) => { ... }), what kind of thing is (req, res) => { ... }?
Special server syntax that only works inside a route
A function passed as an argument, like any other value
A call to a function named req
Correct!
Right. It is an ordinary function used as a value, the same move as passing a function to twice or to setTimeout. The server stores it and calls it later, once per request.
Not quite.
It is not special syntax. It is an ordinary function handed over as an argument, exactly like the one you passed to twice and to setTimeout. Nothing about it is server specific.
Q3. How many arguments are you passing in setTimeout(() => { console.log("hi"); }, 1000)?
One: a line of code to run later
Two: a function, and a number of milliseconds
Three: an arrow, a console.log, and a number
Correct!
Correct. The first argument is a function that has not been called yet. setTimeout holds onto it and calls it after 1000 milliseconds.
Not quite.
Count the commas at the top level. Everything from () to the closing brace is one arrow function, and that is argument one. 1000 is argument two.
Q4. What is the difference between app.get("/users", listUsers) and app.get("/users", listUsers())?
Nothing, the parentheses are optional
The first hands the function over; the second calls it now and hands over its result
The second is the correct way to register a route
Correct!
Correct. Parentheses mean call it now. Without them you are passing the function itself, which is what the server needs so it can call it per request.
Not quite.
Parentheses are how you call a function. With them, the function runs immediately and its return value gets passed along instead. Without them, the function itself is passed.

05
Block Scope
A variable only exists inside its braces. Folder 02. This answers question 3.

Open 02-scope. Before you run node index.js in your terminal, write down what you think the last line prints.

02-scope/index.js
javascript
const isLoggedIn = true;

if (isLoggedIn) {
  const greeting = "welcome back";
}

console.log(greeting);

Read the error message closely. It says ReferenceError: greeting is not defined.

Notice the exact claim. Not that greeting is empty, or unset, or undefined. That it does not exist.

A pair of braces makes a wall. A variable declared with const or let inside { } exists until the closing brace, and then it is gone.

This applies to every pair of braces: an if, a loop, a function body, including the body of your route handler.

+-- your file (module scope) ------------------------+
|                                                    |
|  const users = [];                                 |
|      ... one of these, ever. shared by everybody.  |
|                                                    |
|  +-- handler runs for request #1 ---------------+  |
|  |   const count = users.length;                |  |
|  |       ... created now, gone when this ends   |  |
|  +----------------------------------------------+  |
|                                                    |
|  +-- handler runs for request #2 ---------------+  |
|  |   const count = users.length;                |  |
|  |       ... a different one, unrelated to #1   |  |
|  +----------------------------------------------+  |
|                                                    |
+----------------------------------------------------+

Where a variable is declared decides who can see it and how long it lives

That diagram answers question 3.

A variable declared inside your route handler is created fresh for every request and is private to it.

A variable declared at the top of the file is created once and shared by every request, from every user, for as long as the server runs.

💡

The rule for this module: use const by default, let only when you need to reassign, and never var. var does not respect the wall in the diagram above.

Step 6 of 10
06
Function Scope
Every call gets its own variables. Folder 02.

The same function is called twice with different arguments.

Before you run node index.js in your terminal, decide whether the first call leaves anything behind that affects the second.

02-scope/index.js
javascript
const makeGreeting = (name) => {
  const message = "hello " + name;
  return message;
};

console.log(makeGreeting("Ana"));
console.log(makeGreeting("Ben"));

Each call gets its own private set of variables. message is created when the call starts and destroyed when it ends, and the second call knows nothing about the first.

Parameters work the same way. name is not one variable that gets overwritten. It is a fresh one per call.

Now run node index.js in your terminal again for the second part. There are two variables called message, one inside the function and one outside.

02-scope/index.js
javascript
const message = "I am the outer one";

const shadowDemo = () => {
  const message = "I am the inner one";
  return message;
};

console.log(shadowDemo());
console.log(message);

This is called shadowing. An inner variable with the same name as an outer one hides the outer one for the length of that block.

The outer message is untouched, and you can see it print unchanged on the last line.

💡

This is why two people can hit your /users route at the same moment without their data getting mixed up. Each request runs the handler again, and each run gets its own req, its own res, and its own locals. Anything declared at the top of the file is still shared between them.

Check: Scope
Q1. A variable is declared with let inside an if block and read after the closing brace. What happens?
It prints undefined
It prints the value it was given inside the block
It throws a ReferenceError
Correct!
Right. The braces are a wall. Once the block ends the variable does not exist at all, so JavaScript reports it as not defined rather than as empty.
Not quite.
There is a real difference between empty and non-existent. The variable is not undefined. It is gone entirely, which is why you get a ReferenceError.
Q2. A function declares const total = 0; inside its body. You call that function three times. How many total variables were created?
One, shared by all three calls
Three, one per call, each destroyed when its call ends
One, which keeps its value between calls
Correct!
Correct. Every call builds its own set of locals and throws them away when it finishes, which is why calls cannot interfere with each other.
Not quite.
Variables inside a function body are created when the call starts and destroyed when it ends. Nothing survives between calls, so three calls means three separate total variables.
Q3. In your server file, const users = []; sits at the top and a GET route reads it. Who can see that array?
Only the request that is running right now
Every request, from every user, for as long as the server runs
Nobody, because it is recreated for each request
Correct!
Correct. State at the top of the file is shared by everyone. That is useful when you want it and a serious bug when you do not.
Not quite.
Look at where it is declared. It sits at the top of the file, outside every function, so it is created once when the server starts. Only variables declared inside the handler are fresh per request.

08
for...of
A different style of loop, same reasoning. Folder 03.

Open 03-for-of and run node index.js in your terminal. Two loops, printing the same thing.

03-for-of/index.js
javascript
const fruits = ["apple", "banana", "cherry"];

for (let i = 0; i < fruits.length; i = i + 1) {
  console.log(fruits[i]);
}

for (const fruit of fruits) {
  console.log(fruit);
}

Same output, same reasoning. Both loops walk the array from start to finish.

The difference is what you hold on each pass. The first gives you the position, so you look the item up yourself. The second gives you the item directly.

One question the syntax raises: why is const allowed when fruit is different every time round? Because it is never reassigned. Each pass creates a brand new fruit, uses it, and throws it away.

💡

In this module you may use either one. We will stick to for (const item of ...) because it is much easier to read.

Check: for...of
Q1. In for (const fruit of ["apple", "banana"]), what does fruit hold on the first pass?
The number 0
The string "apple"
The whole array
Correct!
Correct. for...of hands you the item itself, so there is no index to look up.
Not quite.
That is what the counter-style loop gives you. for...of skips the position and hands you the item directly, so the first pass holds the first item.
Q2. Why is const allowed in for (const item of items), when item is different each time round?
Each pass creates a brand new binding, so nothing is ever reassigned
const is ignored inside loop headers
It is a special exception built into for...of
Correct!
Right. There is no exception here. A fresh item is created for each pass and thrown away at the end of it.
Not quite.
Nothing is being ignored and there is no exception. A new binding is created at the start of each pass, used, and discarded. Reassignment never happens, so const is accurate.

Your First Routes, Explained
The three questions, answered

Here is the code from the start of the lesson. Try to answer all three questions yourself before opening the answers.

app.js
javascript
app.get("/users", (req, res) => {
  res.json(users);
});
An ordinary function used as a value. It is the same thing you passed to twice and to setTimeout, spelled the same way. Nothing about the syntax is server specific. You could store it in a const and pass that instead, and the route would work identically.
The server does, once per request, passing in req and res when it does. You handed the function over as an argument and gave up control of when it runs, which is why you never wrote a line that calls it.
At the top of the file, outside every function, which means module scope. It is created once when the server starts and shared by every request from every user, for as long as the server is running. Anything you declare inside the handler instead is private to a single request.

Three lines, three concepts, and none of them are really about servers. Most of what looked mysterious about your route this week was ordinary JavaScript that had not been explained yet.
